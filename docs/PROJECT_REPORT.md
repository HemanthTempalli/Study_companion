# AI Study Companion: Detailed Technical Project Report

## 1. Executive Summary
The **AI Study Companion** is an advanced, full-stack educational platform designed to provide highly personalized, interactive learning experiences. Unlike generic conversational AI tools, this platform restricts the Artificial Intelligence to the user's specific uploaded coursework (PDFs), ensuring all tutoring and assessments are strictly bounded, academically honest, and traceable via citations.

---

## 2. Core Technologies Used
The project leverages a modern, decoupled architecture to ensure scalability, performance, and extremely low operating costs.

### Frontend
* **Next.js 16 (React 19):** Chosen for its App Router, Server-Side Rendering (SSR), and seamless API integration.
* **Tailwind CSS:** Used for utility-first styling to ensure a highly responsive and modern User Interface.
* **Shadcn UI:** Provides accessible, unstyled components (radix-ui) that we customized for a premium look and feel.
* **Recharts:** Used to render complex cognitive graphs and learning analytics (spider charts).
* **Lucide React:** Used for lightweight, consistent iconography.

### Backend
* **FastAPI (Python):** Chosen for its extreme speed, asynchronous capabilities, and native Pydantic validation.
* **SQLAlchemy (Async):** The ORM used to interact with the database asynchronously to prevent blocking the event loop.
* **PyMuPDF (fitz):** Chosen for its blazing-fast, highly accurate text extraction from complex PDF documents.
* **python-jose & passlib:** Used for JWT (JSON Web Token) generation, validation, and bcrypt password hashing.

### Database & Storage
* **PostgreSQL (hosted on Supabase):** A robust relational database.
* **pgvector Extension:** Extends PostgreSQL to store 384-dimensional arrays (vector embeddings) and perform ultra-fast cosine similarity searches directly inside SQL.

### Artificial Intelligence
* **Groq API:** Chosen over OpenAI due to its LPU (Language Processing Unit) architecture, which generates text at ~800 tokens per second, making interactions feel instantaneous. Models used include `llama-3.1-70b` and `qwen-27b`.
* **Sentence-Transformers (`all-MiniLM-L6-v2`):** Runs locally within the backend to convert text into embeddings at zero cost, bypassing the need for paid embedding APIs like OpenAI's `text-embedding-3-small`.

## 3. Application Workflows & Features

### 3.1 Authentication & Authorization
* Users register securely with hashed passwords (bcrypt).
* The system utilizes **Role-Based Access Control (RBAC)**, differentiating between standard `USER` roles and `ADMIN` roles.
* Every API request is verified using stateless JWT tokens passed in the Authorization header.

### 3.2 Workspace Organization (Spaces & Projects)
* **Spaces:** High-level domains (e.g., "Computer Science", "History").
* **Projects:** Specific topics within a Space (e.g., "Neural Networks").
* **Data Isolation:** Every piece of data, chat message, and vector embedding is strictly tied to a `project_id`. The AI is mathematically incapable of accessing data outside the active project, guaranteeing strict data isolation.

### 3.3 Document Ingestion & Background Processing
When a user uploads a PDF, the system offloads the heavy lifting to a background worker to prevent freezing the API.
1. **Extraction:** PyMuPDF extracts raw text from the file.
2. **Chunking:** The text is split into semantic chunks of roughly 500 tokens, with a 50-token overlap to preserve context across boundaries.
3. **Embedding:** The local `Sentence-Transformers` model runs on the CPU to convert each chunk into a mathematical vector.
4. **Storage:** The raw text, page numbers, and vector embeddings are saved to the `document_chunks` table in PostgreSQL.
5. **Concept Extraction:** The LLM scans the document to identify key syllabus topics, creating a foundational "Knowledge Graph" for the student.

### 3.4 Retrieval-Augmented Generation (RAG) Tutoring
When a student asks a question:
1. The question is converted into a vector embedding.
2. PostgreSQL (`pgvector`) performs a mathematical distance search (Cosine Similarity) to find the 5 most relevant chunks from the uploaded PDF.
3. These chunks are injected into the LLM prompt.
4. The LLM generates an answer, strictly citing the source material (e.g., `[Page 12]`).
5. **Hallucination Prevention:** If the retrieved chunks do not contain the answer, the LLM sets a flag (`has_sufficient_evidence: false`) and declines to answer.

### 3.5 Adaptive Assessments
The platform supports two types of quizzes:
* **Multiple Choice:** Dynamically generated by the LLM based on extracted concepts.
* **Open-Ended Evaluation (LLM-as-a-Judge):** The system asks a prompt, the student types a paragraph, and the LLM grades the response against a strict rubric, checking for factual inaccuracies and missing details.

### 3.6 Analytics & Mastery Tracking
* **Cognitive Mastery:** Every quiz score dynamically updates the student's mastery level for specific concepts.
* **Spider Charts:** Visualizes strengths and weaknesses across the syllabus.
* **Recommendations:** The system automatically suggests targeted study sessions for concepts where the student's mastery falls below 60%.

### 3.7 Admin Dashboard
* Provides a high-level view of platform health.
* Displays user metrics, background job success/failure rates, and detailed AI usage logs (latency, tokens, estimated cost).

## 4. Technical Implementation Highlights

### 4.1 Cost-Optimized Database Queue
Traditional background processing requires setting up Redis and Celery, which costs extra money to host. We designed a **DB-backed Job Queue**. Background tasks are inserted into a `background_jobs` PostgreSQL table. A Python worker continuously polls this table using `SELECT ... FOR UPDATE SKIP LOCKED`, allowing atomic, thread-safe job claiming entirely on the free tier.

### 4.2 Single-Container Deployment
To optimize cloud deployment for free tiers (like Render), we bundled the Background Worker directly into the FastAPI `lifespan` event via `asyncio.create_task()`. Furthermore, we restricted PyTorch to a single thread (`OMP_NUM_THREADS=1`) and reduced embedding batch sizes, completely preventing "Out of Memory" (OOM) crashes on 512MB RAM instances.

### 4.3 Structured JSON Outputs
General AI models often fail to return clean data. We enforce strict JSON schemas by heavily engineering the system prompts and passing them through a JSON parser in `groq_provider.py`. If the AI hallucinates markdown formatting (e.g., ` ```json `), our custom regex strips the formatting to prevent backend crashes.

## 5. Conclusion
The AI Study Companion represents a highly optimized, production-ready implementation of a RAG pipeline. By building custom solutions for job queuing and local embedding generation, the system maintains massive scalability while strictly operating within zero-cost cloud environments. It proves that Generative AI can be safely constrained for rigorous, fact-based academic applications.
